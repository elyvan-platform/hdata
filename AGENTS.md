# AGENTS.md

Canonical rules for AI coding agents (Claude Code, Codex, GitHub Copilot) working in hdata.
Tool-specific files (`CLAUDE.md`, `.github/copilot-instructions.md`) are thin adapters and never
override this file.

## 1. Project

A pnpm + Turborepo monorepo: apps in `apps/`, internal packages in `packages/` under the `@hdata` scope.

| Path | Name | Contents |
|---|---|---|
| `packages/config` | config | Config package |

Requirements: Node.js 24 (`.nvmrc`) and pnpm 12.14.0. `elyvan.json` records how
the project was generated; the project never depends on the generator to install, build or run.

## 2. Documents

| Document | Role |
|---|---|
| `AGENTS.md` | Canonical rules (this file) |
| `CLAUDE.md`, `.github/copilot-instructions.md` | Thin adapters — never redefine rules |
| `.github/instructions/*.instructions.md` | Rules per area |
| `.agents/skills/*/SKILL.md` | Task execution guides (`.claude/skills` points to the same folder) |
| `lessons.md` | Operational memory — read the entries of the area before relevant work |

Precedence on conflict: `AGENTS.md` → area instructions → skills.

Area instructions:

- `.github/instructions/typescript.instructions.md` — TypeScript rules for every app and package.
- `.github/instructions/commits.instructions.md` — Use when writing commit messages or preparing branches and pull requests.

Skills live in `.agents/skills/<name>/SKILL.md`; load only the ones whose `description` matches
the task.

## 3. Principles

1. **pnpm only.** Dependency versions live once, in the `catalog` of `pnpm-workspace.yaml`;
   every `package.json` uses `catalog:`.
2. **Shared operational contract.** Every app validates its environment with Zod (`src/env/`,
   `.env.example` generated from it) and keeps the uniform scripts `dev`, `build`, `check`,
   `typecheck`, `test`; every server answers `/health`, `/ready` and `/version`.
3. **TypeScript strict, erasable syntax only.** Biome is the only linter and formatter.
4. **Never swallow errors.** A failure never becomes an empty list, a neutral state or a silent
   exit; distinguish auth errors (401/403) from technical errors (5xx).
5. **No secrets in the repository** or in client bundles.
6. **Use the `elyvan` CLI first.** To add an app, package or capability, or to create a spec, plan
   or ADR, run the matching command (`elyvan add app|package|<block>`, `elyvan new`, `elyvan
   sync`, `elyvan ai sync`, `elyvan doctor`) instead of creating the files by hand or copying them
   from another project. The `elyvan-cli` skill maps every task to its command and lists the
   blocks; read it before changing project structure. Work by hand only when no command covers
   the task, and say in the final report which command you checked.

## 4. Working rules

- Read the relevant code, area instructions and lessons before changing anything; treat a
  diagnosis in a prompt as a hypothesis and verify it against the code.
- Smallest coherent change; no silent scope increase — propose out-of-scope work instead.
- Confirm the behaviour of external libraries and services in their official documentation or
  real output; never invent options, fields or endpoints.
- After three materially different failed approaches to the same goal, stop and report the
  symptom, what was tried and the evidence.
- Update docs when reality changes.

it by hand.

### Model workflow

Every task has two stages, in this order:

| Stage | Claude | OpenAI |
|---|---|---|
| 1. Analyse and plan | Opus | Astra |
| 2. Implement | Sonnet | Sol |

- Always use the latest available version of each model.
- Stage 1 produces the plan (scope, files, approach, risks, validation); do not edit files
  before it exists. Stage 2 implements exactly that plan; if it proves wrong, re-plan.
- A plan with more than one phase is written to disk in the repository (`elyvan new plan
  "<title>"` creates `docs/plans/<slug>.md`) before any phase starts, never kept only in the
  conversation, so other agents or models can continue it. It states what is done and what is
  missing: a status per phase (`Pending`, `Next`, `In progress`, `Done`, `Blocked`), exit
  criteria as checkboxes, the commit of each finished phase and a "Next step" line. Update it in
  the same commit as the work, and read it first when resuming. A phase is `Done` only when its
  exit criteria are validated.
- Trivial tasks still state a one-line plan first. If the tool cannot switch models, say so in
  the final report and keep the plan-then-implement separation.

### Open plans at session start

Plans live in `docs/plans/`, one file per plan, each starting with this header (the `Status` and
`Resume prompt` lines are what agents search for, so keep them exactly in this form):

```markdown
- **Status:** Draft | In progress | Paused | Done | Cancelled
- **Resume prompt:** ask | never
- **Next step:** <the one thing to do next>
```

- A plan is **open** when its `Status` is `In progress` or `Paused`. A `Draft` is not approved
  work; `Done` and `Cancelled` are closed.
- **At the start of every session**, before any other work, list the open plans (for example
  `grep -lE '^- \*\*Status:\*\* (In progress|Paused)' docs/plans/*.md`) and drop the ones with
  `Resume prompt: never`. If any remain, ask the user whether to resume. Show, for each: title,
  `Next step` and phases done out of total; with several, ask which one. Do not start new work
  first, and do not ask again in the same session.
  - **Resume:** read the plan and its log, set `Status` to `In progress` and continue at `Next
    step`.
  - **Not now:** change nothing; it is asked again next session.
  - **Never ask again for this plan:** set `Resume prompt: never` in the plan itself and add a
    log line; the plan stays open but is no longer offered.
- **When stopping** with a plan unfinished (the user ends the work, or the context runs out), set
  `Status: Paused`, update `Next step`, mark the phases accurately and add a line to the plan's
  `## Log` (date, what was done, what is left, anything the next agent must know), in the last
  commit or in a commit of its own.
- When the last phase is `Done` and validated, set `Status: Done`.

### Commits

- Commit each task when it is done and validated: one task, one commit. Never batch tasks and
  never leave a finished task uncommitted.
- Work on a branch, never directly on a protected branch. When on `main`, first create a new
  branch from up-to-date `main`, then apply the changes there; push only when asked.

## 5. Validation

Before declaring a change done, run and report:

```bash
pnpm check       # Biome + .env.example freshness
pnpm typecheck
pnpm test
pnpm build
```

For servers, also start the build (`pnpm start`) and request `/health`. Mobile apps: `pnpm build`
exports the bundles; device runtime is a separate manual check. Report only what actually ran;
a change that was not built is not validated.

## 6. Final report

- Summary of the change and files changed
- Validation: exact commands and the result of each
- What was not validated, why, and the residual risk
- Risks, limitations and follow-ups
